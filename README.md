# IFC2RVT

Плагин Revit, который читает IFC напрямую и создаёт **нативные редактируемые элементы** —
стены, перекрытия, колонны, двери, окна, помещения — вместо мёртвых `DirectShape`, которые
даёт штатный импорт.

[baidurovlabs.ru](https://baidurovlabs.ru) · лицензия [GNU GPLv3](LICENSE)

## Зачем

Штатный импорт IFC в Revit создаёт `DirectShape`: геометрию без параметров, которую нельзя
редактировать, нельзя двигать по-человечески и нельзя считать в спецификациях.

При этом **семантика, необходимая для нативных элементов, в IFC есть** — ось стены, толщина
слоёв, контур плиты, профиль колонны, проём двери. Импортёр Revit её просто выбрасывает.

IFC2RVT читает её сам и строит элементы через Revit API.

## Быстрый старт

```powershell
git clone https://github.com/AnT1pal/IFC2RVT.git
cd IFC2RVT
powershell -ExecutionPolicy Bypass -File install.ps1
```

Скрипт сам собирает проект и раскладывает по всем установленным версиям Revit. Перезапустите
Revit: вкладка **IFC2RVT** → **Конвертация** → **IFC → нативные**.

Перед первым прогоном на незнакомом файле полезно посмотреть, что в нём вообще лежит:

```powershell
dotnet build tools\IfcProbe\IfcProbe.csproj -c Release
tools\IfcProbe\bin\Release\IfcProbe.exe model.ifc report.txt
```

`IfcProbe` работает **без Revit** и за полминуты скажет главное: единицы, вынос модели от нуля,
есть ли у стен ось и слои материалов, связаны ли проёмы с хостом, сколько элементов несут
свойства и цвет. Если стены без `Axis` и без `IfcMaterialLayerSet`, нативных стен из них не
выйдет — и лучше узнать это сразу, а не через полчаса конвертации.

Первый прогон делайте на копии проекта. В диалоге есть **«Ограничить числом элементов»** —
поставьте 50, чтобы посмотреть на результат до полного прохода.

## Что конвертируется

| IFC | Откуда берутся данные | Revit |
|---|---|---|
| `IfcWall` | `Axis` или ось из `IfcExtrudedAreaSolid`, толщина из `IfcMaterialLayerSet` | `Wall` |
| `IfcSlab` | `IfcArbitraryClosedProfileDef` → контур | `Floor` |
| `IfcColumn` | профиль + ось выдавливания | Несущая колонна |
| `IfcBeam` / `IfcMember` | ось выдавливания, профиль из `Description` | Несущая конструкция (по умолчанию выкл.) |
| `IfcDoor` / `IfcWindow` | проём + `OverallWidth`/`OverallHeight` | Вставка в стену нужного габарита |
| `IfcSpace` | контур → центроид | `Room` |
| **всё остальное** | тесселяция тела | `DirectShape` с осмысленной категорией |

Наборы свойств (`IfcPropertySet`, `IfcElementQuantity`, включая свойства типа через
`IfcRelDefinesByType`) переносятся в **общие параметры**, по группе на Pset. Меры
(`IfcLengthMeasure`, `IfcAreaMeasure`, `IfcVolumeMeasure`…) становятся настоящими числовыми
параметрами Revit с правильными единицами, а не текстом — их можно считать в спецификациях.

Служебные параметры на каждом элементе: `IFC GUID`, `IFC Entity`, `IFC Type`, `IFC Tag`.
GUID нужен для повторного импорта с обновлением.

## Честные ограничения

Это не «кнопка, которая делает хорошо». Границы известны заранее:

- **Лестницы, ограждения, витражи** нативно не строятся. Приходят как `DirectShape`.
- **`IfcAdvancedBrep` / NURBS** (в тестовой модели это 10% геометрии) — только `DirectShape`,
  криволинейные поверхности приходят фасетированными.
- **Брак в исходном файле не лечится.** В тестовой модели 313 из 671 `IfcFacetedBrep` ссылаются
  на пустую оболочку `IFCCLOSEDSHELL(())` — ноль граней. Строить там нечего никому, включая
  штатный импортёр Revit. Такие случаи отчёт называет своим именем, а не «не поддержано».
- **Наклонные плиты и колонны** отдаются в `DirectShape`: молча «выпрямить» их хуже, чем
  оставить честную геометрию.
- **Двери и окна требуют, чтобы стена-хост сконвертировалась нативно.** Если стена ушла в
  `DirectShape`, проём тоже уйдёт — дверь в солиде не ведёт себя как дверь.
- **Семейства не создаются, создаются только типоразмеры.** Двери и окна подбираются по
  габаритам из IFC, а если подходящего типоразмера нет — дублируется ближайший и ему
  проставляются ширина с высотой. Само семейство взять неоткуда: если в проекте нет ни одного
  семейства дверей, дверь уйдёт в `DirectShape`. Работайте на шаблоне с нужными семействами.
- **Профили балок не подбираются по сечению.** `L50X3` из `Description` используется как имя для
  поиска, но если такого типоразмера в проекте нет, ставится ближайший и это пишется в отчёт.
  Поэтому балки выключены по умолчанию: неверный профиль на каждом элементе хуже честного
  `DirectShape`.
- **Геометрия отличается на миллиметры.** Нативная стена Revit — параметрический объект, а не
  тот же солид.
- **Переносится ровно то, что есть в файле.** Если экспортёр не выгрузил наборы свойств,
  переносить нечего — чинить надо настройки экспорта у отправителя, а не конвертер.

## Сборка и установка

Нужен .NET SDK 8 или новее.

```bash
dotnet build src/IFC2RVT/IFC2RVT.csproj -c Release
```

Установка во все найденные версии Revit:

```powershell
powershell -ExecutionPolicy Bypass -File install.ps1
```

В конкретную версию:

```powershell
powershell -ExecutionPolicy Bypass -File install.ps1 -Versions 2026
```

После перезапуска Revit: вкладка **IFC2RVT** → **Конвертация** → **IFC → нативные**.

## Кроссверсионность

Две сборки закрывают Revit 2022–2026. Разлом ровно один — среда исполнения:

| Revit | .NET | Сборка |
|---|---|---|
| 2022, 2023, 2024 | .NET Framework 4.8 | `net48`, компилируется против API 2022 |
| 2025, 2026 | .NET 8 | `net8.0-windows`, компилируется против API 2025 |

Различия API закрыты константами `REVIT2024_OR_GREATER` и т.п. в `Directory.Build.props`.
Версионно-зависимого кода — единицы строк (`ElementId.Value` против `IntegerValue`,
`GroupTypeId` против `BuiltInParameterGroup`).

## Архитектура

```
src/IFC2RVT/              ← надстройка, грузится Revit в основной контекст
├─ App.cs                 лента
├─ Commands/              внешняя команда, диагностика, отчёт
├─ UI/                    диалог настроек
├─ Conversion/            КОНТРАКТ: IConversionRunner, ConversionOptions, ConversionReport
│                         (ни одного типа xBIM — в этом весь смысл)
└─ Hosting/CoreLoader     загрузка ядра в изолированный AssemblyLoadContext

src/IFC2RVT.Core/         ← ядро, грузится в приватный контекст вместе с xBIM
├─ Ifc/                   чтение IFC, без зависимости от логики Revit-построения
│  ├─ IfcModelContext     открытие файла, индексы связей, общие ридеры
│  ├─ IfcScale            единицы файла → внутренние футы Revit
│  ├─ PlacementResolver   цепочка IfcLocalPlacement → Transform, с кешем
│  ├─ CurveReader         IfcCurve → кривые Revit (полилинии, дуги, сплайны)
│  ├─ ProfileReader       IfcProfileDef → CurveLoop
│  └─ RepresentationReader Body/Axis/FootPrint, разворачивание IfcMappedItem
├─ Mapping/
│  ├─ RevitTypeName       разбор "Семейство:Тип:Id" из имён Revit-экспорта
│  ├─ LevelMapper         IfcBuildingStorey → Level, плюс подбор по отметке
│  ├─ TypeResolver        поиск типа по имени → по толщине → дублирование
│  └─ MaterialResolver    материалы по имени
├─ Builders/              по одному на вид элемента + DirectShape-fallback
├─ Parameters/            общие параметры и перенос свойств
└─ Conversion/            движок, пакетные транзакции, подавление предупреждений
```

Разделение `Ifc/` и `Builders/` намеренное: слой чтения ничего не знает о том, во что его
результат превратится, поэтому его можно тестировать и отлаживать отдельно.

## Производительность

Модель на 266 МБ / ~17 000 элементов: xBIM открывает её через Esent-базу на диске, а не в
памяти. Транзакции коммитятся пакетами (по умолчанию 500 элементов) — одна гигантская
транзакция на такой модели съедает память процесса на одном только журнале отмены.

Предупреждения Revit (пересечения, незамкнутые помещения) подавляются: без этого конвертация
открывает модальное окно на каждый элемент и не заканчивается никогда.

## Координаты площадки

Модели, выгруженные в общих или городских координатах, оказываются за десятки километров от
внутреннего нуля Revit. **Дальше примерно 16 км Revit теряет точность и перестаёт закрашивать
грани — в 3D видно одни рёбра**, хотя все элементы созданы правильно. Диагностировать это по
виду невозможно: выглядит как сбой геометрии, а на деле сбой отрисовки.

Типичная картина для выгрузки в координатах площадки — тестовая модель лежала в 28 км от нуля:

```
IfcSite origin = (-13 800 000, -24 200 000, 173 000) мм
```

Опция **«Переносить модель к началу координат»** (включена по умолчанию, порог 1 км) сдвигает
всё к нулю по размещению `IfcSite` → `IfcBuilding` → нижнему размещению продукта. На тестовой
модели после сдвига здание занимает X −6.7…70.1 м, Y −11.1…43.4 м, а уровни встают на
0 / 3.4 / 3.52 / 5.58 / 6.8 м — ровно как они названы.

Величина сдвига пишется в отчёт: обратный сдвиг на эти значения возвращает исходные координаты.
`IfcProbe` печатает вынос от нуля в разделе `КООРДИНАТЫ` — проверяйте до конвертации.

Сдвиг записывается в **систему общих координат** через `ProjectLocation.SetProjectPosition`,
поэтому исходное положение площадки остаётся доступно в Revit, а не только цифрой в отчёте.

Именно `ProjectPosition`, а не параметры базовой точки: перемещение самого элемента базовой точки
ограничено теми же 16 км от внутреннего нуля, ради обхода которых сдвиг и делается. Попытка
поставить её на 28 км вызывает модальное окно переноса и не проходит. У общих координат такого
ограничения нет — координаты съёмки штатно измеряются миллионами метров.

## Изоляция зависимостей

Это не теоретический риск, а проблема, которая реально возникла и вот как решена.

xBIM 6 собран против `Microsoft.Extensions.Logging.Abstractions 8.0` и
`DependencyInjection.Abstractions 9.0`. **Dynamo for Revit поставляет те же сборки версий
6.0 и 2.0** и грузится при старте Revit. В .NET 8 контекст загрузки по умолчанию отдаёт уже
загруженную копию независимо от запрошенной версии — xBIM вызывает методы, которых в сборке
Dynamo нет, и `IfcStore` падает в статическом конструкторе с `TypeInitializationException`.
Сам Revit при этом пишет в журнал `Assembly version conflict in some references`.

Решение — разрешать эти зависимости самостоятельно:

- **Revit 2025–2026 (.NET 8):** ядро с xBIM грузится в приватный `AssemblyLoadContext`
  (`Hosting/CoreLoader.cs`). Он отдаёт из папки надстройки всё, кроме Revit API и самой
  `IFC2RVT.dll` — те намеренно делегируются в контекст по умолчанию, иначе `Document` и `XYZ`
  по разные стороны границы оказались бы разными типами.
- **Revit 2022–2024 (.NET Framework):** там связывание идёт по точной версии, поэтому чужая
  копия просто не подойдёт. Достаточно обработчика `AssemblyResolve`, отдающего сборки из
  папки надстройки.

Отсюда и деление на две сборки: `IFC2RVT.dll` содержит только контракт
(`IConversionRunner`, `ConversionOptions`, `ConversionReport`) и не ссылается на xBIM вообще.

это ровно все стены, все плиты и начало колонн.

## Инструмент проверки

`tools/IfcProbe` — консольная утилита, которая читает IFC **без Revit** и печатает, что в нём
на самом деле лежит: единицы, этажи, наличие `Axis` у стен, слои материалов, связи проёмов,
покрытие наборами свойств.

```bash
dotnet build tools/IfcProbe/IfcProbe.csproj -c Release
tools/IfcProbe/bin/Release/IfcProbe.exe model.ifc report.txt
```

Запускайте его **до** конвертации на незнакомом файле. Если стены без `Axis` и без
`IfcMaterialLayerSet`, нативной стены из них не выйдет, и лучше узнать это за 30 секунд,
а не через полчаса конвертации.

## Отчёт

После конвертации плагин показывает сводку и пишет CSV во временную папку: по каждому элементу
его IFC GUID, сущность, результат (нативно / DirectShape / пропущено / ошибка), созданный
элемент Revit и причина, если нативно не вышло. По этому CSV видно, где конвертер упирается
в конкретную модель.
